# 功能規格書

## Metadata

- 功能：網站可信度與功能健全化
- 負責人：Squall／Codex
- 狀態：人工已核准（Squall／2026-09-13）
- 風險等級：中

## 問題

Runner Plaza 的訓練核心與主要互動雖可運作，但目前存在六個會降低可信度或阻斷完整驗證的缺口：正式賽事資料庫與網站副本不一致、手機賽事卡過高、本機／遠端資料新鮮度不可見、10K 賽後教練閉環需要明確且保守、部分賽事欄位語意不完整，以及 Node／Python 驗證入口不一致。使用者無法只看頁面就判斷資料是否最新，維護者也無法用單一指令取得可靠的整體結果。

## 使用者

- 主要使用者：檢視賽事、訓練課表與 Garmin 判讀的跑者。
- 次要使用者：維護 Runner Plaza 資料與發布流程的人員。

## 目標

- 讓公開網站只發布與正式賽事資料庫完全一致的賽事資料。
- 讓 390px 手機上的賽事卡保留必要決策資訊，同時通過既有高度門檻。
- 顯示可理解的資料最後更新時間與同步狀態，不把舊資料呈現成已同步。
- 讓 10K 賽後依 Garmin 證據與 48 小時恢復訊號進入既有教練決策，不因單場成績自動升級。
- 對不完整的費用、名額或來源資料標示「待確認」，避免假精確。
- 提供一個可重跑的整體驗證入口，統一使用專案既有的 `uv` Python 環境。

## 非目標

- 不改變半馬 2:15 目標與已確認的 W11 正式課表。
- 不自動提交、推送、部署或覆寫使用者現有未提交資料。
- 不重寫爬蟲架構、不新增第三方 UI framework，也不建立第二套教練課表引擎。
- 不因單一 10K 成績直接修改 E／T／I 或半馬目標配速。
- 不要求跑者重複輸入 Garmin 已提供的資料。

## 使用者故事（User Stories）

| 故事 | 身為／我想要／以便 | 驗收標準 |
|---|---|---|
| US1 資料一致發布 | 身為維護者，我想讓正式資料庫成為唯一發布來源，以便網站不漏賽事或混用舊資料 | 發布／完整驗證前比較正規化內容；不一致時阻擋並列出差異；同步後兩檔逐位元一致 |
| US2 精簡手機賽事卡 | 身為手機使用者，我想先看到日期、名稱、距離、報名狀態與主要操作，以便快速決策 | 390px 下既有測試資料的卡片高度通過門檻；完整費用、名額、組別仍可由可及性良好的展開區讀取 |
| US3 資料新鮮度 | 身為跑者，我想知道資料何時更新及是否同步，以便判斷是否可採信 | 顯示最後更新時間與正常／待同步／載入失敗狀態；無時間資料時不得顯示虛構日期 |
| US4 賽後教練閉環 | 身為跑者，我想在 10K 後得到保守且有證據的下一步，以便避免單場跑快造成過度升級 | Garmin 成績先保存為證據；未滿 48 小時、缺 RPE／恢復訊號或有疼痛時維持或降載；證據完整才允許既有校正流程評估 |
| US5 不完整資料標示 | 身為賽事使用者，我想辨識尚未核實的費用／名額，以便不把解析殘片當正式資訊 | 偵測到呈現品質問題的欄位顯示「待確認」與既有來源連結；不隱藏已知可靠欄位 |
| US6 單一驗證入口 | 身為維護者，我想用一個指令完成前端、資料、建置與 Python 測試，以便避免環境差異造成假失敗 | 新指令序列執行語法／smoke、layout、Trainer、資料一致性、Vite build、`uv run pytest -q`；任一項失敗即非零結束 |

## 使用者旅程

```text
身為 Runner Plaza 跑者
我打開網站先確認資料更新狀態，再以精簡卡片挑選賽事；需要時展開完整資訊。
完成 10K 後，系統接收 Garmin 證據並等待必要恢復訊號，由同一教練決策流程給出維持、降載或可評估校正的結果。
以便我不會被舊資料、不完整欄位或過度積極的單場判讀誤導。
```

## 功能需求

- WHEN 網站資料準備發布或執行完整驗證，THE SYSTEM SHALL 將 `runner/賽事/賽事資料庫.json` 視為正本，驗證 `site/data/races.json` 與其一致。
- WHEN 兩份賽事資料不一致，THE SYSTEM SHALL 以非零狀態阻擋完成宣告並輸出可定位的新增、刪除或變更項目。
- WHEN 使用者以 390px 寬度瀏覽賽事列表，THE SYSTEM SHALL 將次要事實放入既有可展開區，保留主要報名與收藏操作。
- WHEN 頁面資料成功載入，THE SYSTEM SHALL 顯示來源提供的最後更新時間與同步狀態；沒有可信時間時顯示「更新時間未提供」。
- WHEN 資料載入失敗，THE SYSTEM SHALL 顯示錯誤狀態與現有安全重試路徑，不沿用「已更新」狀態。
- WHEN 9/20 10K Garmin 活動到達，THE SYSTEM SHALL 保存比賽證據並沿用既有 race assessment、recovery 與 promotion gate。
- WHEN 48 小時恢復證據不足或存在疼痛、步態異常、嚴重疲勞，THE SYSTEM SHALL 禁止配速升級並維持或降載。
- WHEN 賽事費用或名額無法對應組別，THE SYSTEM SHALL 顯示待確認語意，不直接把解析片段當成完整事實。
- WHEN 維護者執行完整驗證，THE SYSTEM SHALL 使用 `uv run pytest -q`，不依賴全域安裝的 pytest。

## 資料與 API

- 輸入：`runner/賽事/賽事資料庫.json`、`site/data/*.json`、Garmin 活動與恢復資料、既有教練設定。
- 輸出：一致的公開賽事 JSON、資料狀態呈現、賽後教練決策、整體驗證結果。
- 驗證：JSON 可解析、賽事正本／副本一致、更新時間合法、未知欄位安全降級、教練 gate 不越權升級。
- 錯誤：資料不一致、載入失敗、缺少時間、Garmin 證據不足均採 fail-visible／fail-closed，不宣稱成功。

## 安全性與隱私

- 身分驗證：沿用現有公開頁／本機 Garmin 配對邊界，不新增登入機制。
- 權限：公開頁只讀公開衍生資料；私人 Garmin 原始資料與報名個資不得加入公開 JSON。
- 敏感資料：只呈現彙整教練證據；不得新增活動原始串流、token 或本機個資輸出。
- 濫用情境：阻止外部頁面取得本機配對資訊；資料狀態不得讓任意來源字串注入 HTML。

## 驗收標準

- `runner/賽事/賽事資料庫.json` 與 `site/data/races.json` 在受控同步後內容一致，未同步時測試明確失敗。
- `npm run ui:layout` 的手機賽事卡密度檢查通過，且桌面與手機仍能取得完整賽事資訊。
- 賽事頁在資料正常、過期／待同步、缺少時間與載入錯誤時都有明確狀態。
- 9/20 賽後未滿足證據門檻時，不修改既有配速區間或解鎖 I 課。
- 不完整費用／名額不再以無組別數字冒充完整資訊。
- 一個整體指令可重跑全部既有前端／Trainer／資料／build／Python 驗證。
- 不改寫歷史課表、已完成課程、W11 正式菜單或使用者現有未提交資料。

## 驗證計畫

- 單元測試：擴充 Trainer promotion／race recovery 邊界與賽事資料狀態格式測試。
- 整合測試：正式賽事正本／網站副本一致性、資料載入正常／失敗、完整驗證入口退出碼。
- E2E：既有 `ui-smoke-check.mjs`、`ui-layout-check.mjs`、`trainer-logic-check.mjs` 與本機 HTTP 回應。
- 視覺：桌機與 390px 賽事列表；資料正常、待同步、錯誤；Trainer 賽後等待與阻擋狀態。
- 手動：確認完整資訊仍可展開、鍵盤焦點可操作、Garmin 已提供資料不重複詢問。
