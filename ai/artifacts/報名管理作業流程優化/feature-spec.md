# 功能規格書

## Metadata

- 功能：報名管理作業流程優化
- 負責人：Squall
- 狀態：已核准，實作完成
- 風險等級：中（本機保存身分與付款資料；不改資料格式）

## 問題

隊務操作者建立隊員、帶入賽事及更新繳費時，需要自行理解欄位關係與下一步。首次建檔的必填個資被收在折疊區；賽事狀態又可能和隊員報名／付款進度互相矛盾。既有功能完整，但填寫與後續追蹤仍有不必要的判讀成本。

## 使用者

使用本機 Runner Plaza 管理隊員報名、繳費、通知與 Excel 批次資料的隊務操作者；主要使用桌面，需保有手機可操作性。

## 目標

- 讓首次隊員建檔明確完成所有必要個資，不因收合區塊而無法儲存。
- 賽事帶入後，操作者在同一工作流程完成選人、選組別與建立紀錄。
- 將賽事開放狀態與個別隊員的報名／付款進度清楚分離，避免儲存矛盾資料。
- 讓報名管理的專用驗證反映目前模組化程式結構。

## 非目標

- 不修改 `/api/registration-data`、批次 Excel、JSON 備份／還原、資料 schema、localStorage key 或本機存取限制。
- 不新增帳號、雲端同步、金流串接或真實訊息發送。
- 不重做通知工作台、歷史紀錄或視覺風格。

## 使用者故事

| 故事 | 身為／我想要／以便 | 驗收標準 |

| US-01 | 身為隊務，我想在首次新增隊員時看見全部必填資料，以便一次完成主檔 | 必填欄位皆可見；未填欄位會被指出並聚焦；既有人員編輯仍可收合敏感欄位 |

## 使用者旅程

```text
選擇賽事 → 帶入賽事 → 選擇隊員 → 選擇組別 → 建立紀錄
                                     ↓
                              更新報名／付款進度 → 待辦與通知
```

## 功能需求

- WHEN 新增隊員，THE SYSTEM SHALL 展開「聯絡與緊急資訊」並顯示建檔完成提示。
- WHEN 隊員表單有隱藏的必填欄位未填，THE SYSTEM SHALL 展開該區、顯示摘要並將焦點導向第一個欄位。
- WHEN 帶入賽事，THE SYSTEM SHALL 在報名表單呈現「選人、選組別、建立」三步引導，且不變更已帶入欄位。
- WHEN 儲存付款狀態但未勾選已報名，THE SYSTEM SHALL 拒絕寫入並說明如何修正。
- WHEN 報名／付款日期或金額存在，THE SYSTEM SHALL 僅作輔助資訊，不自行改寫既有記錄。
- WHEN 執行專用驗證，THE SYSTEM SHALL 檢查 `registration.js` 與其 actions/render/data/core 模組的實際責任歸屬。

## 畫面

|---|---|---|
| 隊員首次建檔 | 預設、錯誤、停用、行動版 | 既有資料不得洩漏至公開頁 |
| 報名建立 | 預設、空人員、帶入成功、錯誤、行動版 | 三步引導與多人選取共存 |

## 資料與 API

- 輸入：既有 `people`、`entries` 表單欄位與賽事資料。
- 輸出：維持既有 `people`、`entries` JSON 結構。
- 驗證：補上付款不可早於報名完成的狀態一致性規則。
- 錯誤：沿用既有 status message、focus、toast 與本機 API 錯誤處理。

## 安全性與隱私

- 身分驗證與權限：維持 loopback-only，無帳號變更。
- 敏感資料：身分證、手機與緊急聯絡資料僅顯示於本機操作頁；列表遮罩規則不變。
- 濫用情境：不新增任何外送、分享或公開 URL。

## 驗收標準

- 所有既有資料、Excel 批次匯入匯出與備份還原維持相容。
- 首次建檔不會因折疊的必填欄位造成無法理解的原生驗證阻擋。
- 帶入賽事後可在不離開報名工作區的情況下完成第一筆或多人報名。
- 不可寫入 `isPaid: true` 且 `isRegistered: false` 的新紀錄。
- 專用驗證及既有 UI 檢查通過，並完成桌機及手機視覺檢查。

## 驗證計畫

- 單元測試：報名／付款狀態一致性與表單錯誤處理。
- 整合測試：更新 `validate-registration-manager.mjs` 的模組責任檢查。
- E2E：本機伺服器下的建立隊員、帶入賽事、多人建立與錯誤路徑。
- 視覺：1440px 與 390px 檢查預設、錯誤、空狀態。
- 手動：確認 API、Excel、備份／還原及鍵盤 tab 行為不變。
