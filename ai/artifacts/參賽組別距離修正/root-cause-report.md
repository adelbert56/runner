# W15 跑量反覆不一致：根因分析

> 歷程註記：以下為修復前的根因快照。使用者後續已核准修復，交付證據見 `verification/PLAN-TRUTH-002.md`。原重現腳本現已轉為生命週期驗收，不再預期錯誤行為通過。

日期：2026-10-18。範圍：讀取目前程式、既有 W15 正式週報與歷史修復紀錄；執行 VM 隔離實驗。未操作使用者瀏覽器、未部署、未新增正式程式變更。本輪新增本報告與重現腳本。

## 結論

根因是課表沒有在所有寫入端、讀取端共同落實同一份決策結果。賽事整合與教練處方分別直接修改 appData.plan；教練資料載入時又啟動未等待完成的賽事同步。部分畫面讀解析後課程，部分統計讀儲存底稿，因此同一週可能同時存在 26K／四堂與 20K／三堂。

這不是 JavaScript 浮點數、快取或加總公式出錯。快取版本更新只能讓新程式載入，不能解決資料互相覆蓋。

## 已確認的因果鏈

1. **51.2K 的觸發點**：`site/trainer.js:285` 的參賽距離來源，未取得明確組別時仍回退公開賽事最大距離。臺中公開資料同時列 42.195／21／11／4K；它不是跑者報名組別。原先恢復底稿的非賽日只有 0＋5＋4＝9K，配上誤抓的全馬就是 51.195，顯示 51.2K。修正參賽距離只把這個狀態降到 20K，無法補回正式日課。
2. **20K 的觸發點**：通用賽後恢復把週一改休息、週二上限 5K。原本的 coachPrescription 對 post-race 直接退出，所以正式週一 5K、週二 6K 無法套用。正式菜單是 5＋6＋4＋11＝26K；底稿是 0＋5＋4＋11＝20K。
3. **前次補修仍會留下不同版本**：`site/trainer.js:3104` 呼叫 async syncRegisteredSundayRaces，未等待就進行 `materializeCoachReviewWeek`。有報名資料時賽事同步會等待 fetch，之後才執行通用恢復寫入。實驗確認：先 materialize 得 26K，延遲 fetch 完成後底稿變 20K。目前的 resolver 修補仍能把畫面用日課解析回 26K，但不代表儲存底稿也保持一致。
4. **摘要讀取混用**：`site/trainer-coach-engine.js:115` 的完成統計、`:128` 的計畫堂數直接讀底稿；週目標透過 `effectiveWeekVolumeTarget` 讀 resolver。隔離實驗中同一份狀態底稿三堂、解析後四堂。只驗證總公里數會漏掉堂數與完成率問題。
5. **權限／優先序沒有共同執行**：`site/trainer-plan.js:1176` 宣告課表變更單一權威，但賽事整合與 materialization 沒有共同透過該決策。實驗中同一個 post-race 日，planDayLockReason 對 coach 回傳鎖定，coachPrescription 卻可回傳 5K。這顯示通用保護、正式處方與歷史鎖定的優先序仍分散於不同函式，修一個入口不能保證其他入口同步。

## 為何多次修補仍漏掉

- W12 曾修過「29K 每日課程對上 36K 舊目標」及切週完成率，當時把週目標改為 resolver 加總，但沒有讓所有完成統計／寫入流程一起收斂。
- 本次第一輪只驗證 11K 距離與手組 5／6／4／11K 的算式，沒有從已被 post-race 改寫的儲存狀態走完整流程。這是交付驗證不足。
- 第二輪增加真實 resolver/materialize 測試，能修正靜態 20K 底稿，但未加入 materialize 後延遲完成的賽事同步。
- smoke checks 多為原始碼字串斷言；發布檢查只驗菜單內部距離、步驟與週目標。兩者都不會執行瀏覽器已有的舊狀態與非同步覆寫。
- 因此「138 項邏輯測試與 197 項 smoke 全過」不能當作上述完整生命週期已通過的證據。前兩次完成陳述應以此限縮。

## 修復邊界與驗收契約

建議下一批修復限制在這些已確認的缺口，不改訓練內容或新增版面：

1. **統一決策與寫入邊界**：賽事同步不得直接破壞已確認的 dated recovery 處方；將通用恢復與正式恢復的優先序集中到既有決策層。不能只補一個 await，因為 storage 事件與其他呼叫點仍會再次同步。
2. **統一讀取結果**：每日卡片、目標公里、排定堂數、完成／部分完成與 Garmin 匯出，都從同一份所選週的解析結果取值。保留實跑與手動認列的權威；避免只把分母強制改成 26。
3. **組別資料不可猜測**：明確保存參賽距離；未確認多組別時不得把公開最大距離當個人距離。需定義未知狀態與既有資料升級策略，不能用半馬目標距離替代另一個猜測。
4. **歷史與保護規則一致**：分清楚通用恢復、明確安全保護、正式 dated 處方與歷史凍結；任何校正只修來源錯誤，不重寫當時實跑與完成紀錄。

必要回歸：賽事同步先／後完成、重複 storage 同步、儲存重載、週報尚未解鎖／解鎖後、當週轉歷史週、無組別、多組別、明確傷痛保護與未定日菜單。每個階段共同檢查每日卡片、週公里、排定堂數、完成／部分完成與實跑原始證據。有效保護導致減量時，應能追到日期與原因，不能把所有週強制湊回原始目標。

## 審查判定

- P1：延遲賽事同步可覆寫正式儲存處方；日課與統計分別讀兩份結果。
- P1：未知個人組別仍回退公開最大距離，可能錯誤影響課表與恢復天數。
- P2：多處優先序不一致；目前測試與發佈檢查未涵蓋完整生命週期。
- 判定：目前不能宣告系統性問題已根治。前兩輪屬局部修補；本輪完成根因鑑識及可重現證據，未擴大實作上述跨檔修復。
- 未驗證：使用者瀏覽器的實際 localStorage、當時請求時序與正式部署版本。不得把可重現的程式缺口說成已讀到該瀏覽器的現場紀錄。
